# What harness2 writes, and where it lands

Every file and key harness2 writes per sweep, per task, per mode and per rollout, for the two cells `h2real.py` builds: JobBench with OpenCode (`jb`, `oc`) and LAB with Codex (`lab`, `cx`), k = 2, both modes, the library on. `test_h2real.py` reads this table. Each key the fixture writes must have a row, and each row must be written by the cell it applies to. Each row cites the harness2 line that writes the key, or that reads it when another program writes the file. A key that is not imported says why.

Conventions:
- `h2:` is the read-only harness2 clone at 1cfe254 (`ops/harness2-1018/src/harness2`). Nothing here ran it.
- `<B>` is either bench folder. A pattern under `jb/` or `lab/` is that bench's only. A trailing `(oc)` or `(cx)`, or `results/<sub>/`, is that substrate's only.
- In keys, `*` is one map key (a mode, an anonymous id) and `[]` is a list of objects. `(file)` and `(tree)` are a file or folder whose content is not parsed.
- NS is the row ext `dev.loopmath.adapter.harness2` (loopmath's own labels). REC is the row ext `com.github.google-research.harness2`, which holds harness2's own records as harness2 wrote them, and is written only under `loopmath adapt harness2 --privacy full`. Its strings make a run `full` (spec/harness-runs.md). By default (`--privacy metadata_only`) NS keeps their text-free part (`stage`, `selection`, `crash_kind`), text is left out of the summary too, and the summary counts what it withheld.
- "summary" is the `loopmath adapt harness2 --json` summary's `experiments[]` entry, which is not stored.

## What harness2 does not log that the gate needs

1. **A score per rollout during the loop.** `score()` is "called only by `core.judge`, only after selection committed" (h2:harness2/core/spec.py:247-250). Only the adopted stage and the bases are judged, after the sweep, by a separate command (h2:harness2/cli/judge.py:118-144, 186-192). The gate needs a score for every base and final replicate, at decision time. The 0002 patch's ask loop and the hook's `outcome` supply it.
2. **A cost per rollout.** Each rollout is recorded at 0 USD (h2:harness2/core/ledger.py:58), so `rollout_usd` is always 0. The reader counts each rollout's spend from its streams. Codex streams carry tokens and no dollars (h2:harness2/substrate/codex.py:432-443), so a `cx` rollout's dollars always come from loopmath's price table.
3. **Replicates.** Each tree runs once: R = 4k, which is k shared bases, 2k candidates and k finals (h2:harness2/core/ledger.py:26-28). The gate needs paired replicates of the final and the incumbent on the same task.
4. **The pairing.** Nothing records which base rollout a final is compared with. The selector compares the candidates' deliverables under anonymous ids (h2:harness2/core/selection.py:294-305), and no score pairs them. The gate needs each pair named.
5. **A dead rollout's error.** A rollout that died before its runner made a folder leaves only `run_dir` `<task dir>/missing` (h2:harness2/core/schedule.py:622, h2:harness2/core/recursion.py:293), from a RunView built in memory (h2:harness2/core/schedule.py:424-427). No RunView or error text is written (h2:harness2/core/recursion.py:79-105). The gate can count the death but not tell a crash from a timeout.
6. **A crashed mode's spend.** A mode that raises gets `{ok, error, traceback}` in place of its stages and ledger (h2:harness2/core/schedule.py:655-659). Its editor spend and the list of rollouts it ran are gone. The reader recovers the rollouts from `harnesses/` (h2:harness2/core/recursion.py:274-276), but not the stage spend.
7. **Start times for JobBench with OpenCode.** There is no runner config with a start time. Times come only from the stream's `timestamp`s (h2:third_party/lab_runner/opencode/session.py:81), so a rollout with no events has no time.
